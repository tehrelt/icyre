# api/proto

Protobuf-контракты внутренних gRPC API ICYRE (EPIC-034). Сгенерированный Go/gRPC-код попадает в `libs/contracts/gen`.

## Структура

- `catalog/v1/catalog.proto` — `catalog.v1.CatalogService` (артисты, альбомы, треки, жанры, batch- и cursor-выборки)
- `users/v1/users.proto` — `users.v1.UsersService` (публичный и собственный профиль пользователя)
- `playback/v1/playback.proto` — `playback.v1.PlaybackService` (сессия воспроизведения, очередь, состояние, события)

Конфигурация Buf v2 находится в корне репозитория: `buf.yaml` (`STANDARD` lint, `FILE` breaking) и `buf.gen.yaml` (`protoc-gen-go`, `protoc-gen-go-grpc` с `paths=source_relative`).

## Инструменты и команды

Версии инструментов зафиксированы в `Makefile` (`BUF_VERSION`, `PROTOC_GEN_GO_VERSION`, `PROTOC_GEN_GO_GRPC_VERSION`) и устанавливаются локально в `.tools/bin`:

- `make proto-tools` — установить зафиксированные `buf`, `protoc-gen-go`, `protoc-gen-go-grpc` в `.tools/bin`
- `make proto` — отформатировать `.proto` (`buf format -w`) и перегенерировать код в `libs/contracts/gen` (`buf generate --clean`)
- `make proto-lint` — проверить `buf lint` и `buf format --diff --exit-code`
- `make proto-check` — убедиться, что `libs/contracts/gen` соответствует текущим `.proto`
- `make proto-breaking` — проверить обратную совместимость против `PROTO_BASE_REF` (по умолчанию `origin/main`)

## Политика обратной совместимости (`v1`)

Все контракты в пакетах `*.v1` обязаны сохранять wire-, source- и семантическую совместимость. Контроль разделяется на два уровня:

- **Автоматическая проверка в CI (`buf breaking`, правило `FILE` в `buf.yaml`)** — проверяет wire- и source-совместимость схемы: номера, типы и имена полей, имена сообщений/сервисов/enum, `package` и `option go_package`, сигнатуры RPC.
- **Ручное ревью владельцем сервиса (service-owner review)** — обязательно для семантических и поведенческих изменений, которые `buf breaking` не отслеживает: единицы измерения (например, `ms` vs `s`), scope и правила авторизации, порядок сортировки, семантика пагинации, поведение retry и идемпотентности.

### Запрещено в `v1`

1. **Удалять или переиспользовать номера и имена полей.** Устаревшие поля и RPC в `v1` не удаляются — их оставляют на месте с опцией `[deprecated = true]` для сохранения source-совместимости. Удаление допустимо только в новом мажорном пакете (`v2`) или при pre-release очистке до публикации контракта; при таком удалении номер и имя поля должны быть зарезервированы:
   ```protobuf
   reserved 9;
   reserved "legacy_field";
   ```
2. **Менять тип или семантику существующего поля/RPC** (например, `int32` → `int64`, `string` → `bytes`, скаляр ↔ `repeated`, а также единицы измерения вроде `ms` → `s`, scope авторизации, порядок сортировки, семантику пагинации или retry/идемпотентности).
3. **Удалять или переименовывать** существующие `service`, `rpc`, `message`, `enum` и значения `enum` в рамках `v1`.
4. **Менять нулевое значение `enum`** — значение `0` всегда остаётся `*_UNSPECIFIED = 0`.
5. **Менять `package` или `option go_package`** в существующих файлах `v1`.

### Разрешено в `v1` (безопасная эволюция)

1. **Добавлять новые поля** в существующие сообщения с новыми уникальными тегами.
   - Для опциональных/nullable полей и partial-update запросов (`UpdateMyProfileRequest`, `UpdateStateRequest`) использовать `optional` (explicit presence).
   - Потребители обязаны корректно обрабатывать отсутствие новых полей (zero value / unset `optional`).
2. **Добавлять новые значения `enum`** с новыми числовыми тегами. Серверы и клиенты обязаны иметь fallback для неизвестных значений `enum`.
3. **Добавлять новые `rpc`-методы** в существующий сервис (с уникальными `<Method>Request` и `<Method>Response`) и новые сообщения.
4. **Помечать устаревшие поля и RPC** опцией `[deprecated = true]` с комментарием о замене, сохраняя их в `v1` для source-совместимости; удаление выполняется только при переходе на `v2`.

## Политика эволюции до `v2`

Если требуется несовместимое изменение (удаление/переименование полей или RPC, смена типов, перестройка модели данных или контракта пагинации/ошибок):

1. **Создаётся новый версионированный пакет** `api/proto/<domain>/v2/<domain>.proto` с `package <domain>.v2;` и `option go_package = "github.com/tehrelt/icyre/libs/contracts/gen/<domain>/v2;<domain>v2";`.
2. **Параллельная работа (`v1` + `v2`).** Сервер реализует и регистрирует оба сервиса (`v1` и `v2`) на период миграции всех потребителей.
3. **Deprecation-окно.** Устаревшие элементы `v1` помечаются `[deprecated = true]`, новые клиенты подключаются только к `v2`.
4. **Вывод `v1` из эксплуатации** выполняется отдельным изменением только после подтверждённого перевода всех сервисов-потребителей на `v2` и отсутствия трафика на `v1`.
